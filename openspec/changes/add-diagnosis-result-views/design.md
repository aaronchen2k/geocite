## 背景

当前 GEO 工作台已经提供导航占位页和系统管理实体，但没有诊断运行、诊断数据或诊断结果展示。GeoLook 的实现证明诊断必须同时保留原始证据、可复算规则和可操作的优先级：站点问题按“访问 → 定向 → 理解 → 可引用”依赖排序；AI 可见性问题再按内容、阵地、事实三类聚合；验证结果必须对照当期和基线，而不是只展示单一分数。

本变更将这一闭环转换为 NestJS + SQLite API 和 Next.js 管理台。`Brand` 是诊断边界；每次运行和其结果快照独立保存。采样/爬虫适配器可以在首期以导入结果或受控模拟实现，不能伪造实时外部 AI 数据。

## 目标与非目标

**目标：**

- 定义统一的诊断运行、证据、发现项、结果快照和验证比较模型，所有结果均归属一个未删除 Brand。
- 将站点检查结果表示为四层依赖模型，并显示问题证据、受影响页面、修复建议、严重度和阻塞关系。
- 将问题级 AI 可见性数据和内容、阵地、事实数据聚合为按固定优先级排序的差距诊断。
- 为诊断概览、资产审计、渠道地图、引用检测、综合报告和验证页面提供可筛选、可追溯的读 API；所有时间采用 UTC 存储、浏览器本地时间展示。
- 使用不可变快照完成周期/问题/工单的前后对比，未采样或无法自动判断时显式显示“未测/待人工”，不视为 0 或失败。

**非目标：**

- 不在本变更中实现真实引擎账号登录、绕过反爬、自动内容生产、自动外部发布或自动修复网站。
- 不承诺以一个聚合分数代替原始证据，不在样本不足时生成确定性结论。
- 不实施多租户、计费、团队审批流或完整工单执行界面；只预留诊断到工单/验证的关联数据。

## 设计决策

1. **采用“运行 + 不可变快照 + 派生发现项”模型。** `DiagnosisRun` 记录品牌、触发方式、规则版本、数据覆盖和状态；站点/采样原始证据挂在运行下；`DiagnosisSnapshot` 保存展示所需聚合结果和基线引用。这样结果可复核和重算，优于只更新当前汇总表；相对完整事件溯源，实现成本可控。

2. **将诊断规则服务化、版本化。** `SiteDiagnosisService` 输出四层状态和 `SiteFinding`；`VisibilityDiagnosisService` 输出问题诊断与三类缺口。每个发现保存 `ruleCode`、`ruleVersion`、计算输入摘要和证据引用。首期规则与 GeoLook 对齐：疑似负面 > 竞品主导 > 完全缺席 > 排名靠后 > 正常；替代方案是用 LLM 黑盒判定，但它不能稳定解释或回归测试。

3. **按 Brand 隔离且沿用软删除约束。** 任何创建、查询或关联诊断数据的 API 必须先验证 `Brand.deleted = false`；列表和详情默认排除软删除的运行及子记录。这样与现有 Brand 管理行为一致，避免删除品牌后仍能展示可操作数据。

4. **读模型按页面任务分解，不暴露持久化细节。** `GET /brands/:brandId/diagnoses/latest` 提供概览；四层资产审计、差距、阵地、问题结果与验证趋势各有分页/筛选端点。前端以 URL 查询参数保存 market、severity、layer、runId 和 questionId，使跨页“查看证据/创建工单/查看前后变化”可深链。相比一个巨型 dashboard API，可独立加载和扩展；相比前端聚合，可保证指标口径一致。

5. **验证使用基线与当前快照的显式比较。** `VerificationResult` 关联目标、检查器表达式、基线值、当前值、目标、结论和人工原因。自动检查无法获得输入时结论为 `unmeasured`，人工检查为 `manual_required`；不以 `0`、`false` 或成功默认值替代缺失数据。

6. **保留导入边界，延后采集器。** 首期诊断运行接受结构化站点审计和采样结果导入，并为未来 `Engine` 适配器预留 `engineId`、来源方式和采样环境字段。这样可用受控样本交付 UI/规则/结果闭环，又不把未获授权的平台采集伪装成产品能力。

## 风险与取舍

- [站点/引擎数据缺失导致误导性 0 分] → 每个指标保存样本数和测量状态，UI 统一显示“未测”。
- [规则升级改变历史结论] → 运行和快照保存规则版本；升级后新建运行，历史结果保持不变。
- [四层问题和三类缺口重复计数] → 站点发现与可见性发现使用不同类别；概览明确来源，交叉关联仅作链接。
- [诊断数据量大、页面加载慢] → 原始证据分页，快照只存汇总；大文本/抓取正文作为独立证据资源按需加载。
- [事实偏差和负面线索误报] → 保留原文片段与人工复核状态，标签文案使用“疑似”且不可自动定性。
- [外部平台合规与稳定性] → 仅接入获授权的采样方式；记录来源、环境、失败原因和最后成功时间。

## 迁移计划

1. 为诊断运行、站点证据、页面发现、问题指标、阵地覆盖、事实比对、快照和验证结果建立带 `brand_id`、软删除和 UTC 审计列的表。
2. 先以迁移/seed 导入一份可复现的示例诊断数据，完成 API 契约和管理台空态/结果态。
3. 上线读 API 和 UI 后，再接入受控站点抓取与采样导入；每个采集器以 feature flag 启用。
4. 回滚时关闭诊断运行入口和新导航，不删除历史快照；现有 Brand/Engine/Model/RagAgent API 无协议变更。

## 分期交付路线

当前已具备的基础能力是：品牌级诊断问题与 sitemap 抓取上限配置、一次诊断运行的站点请求/基础 HTML 信号/引擎采样证据保存，以及诊断配置、执行和报告三个路由。报告仍为示例展示，尚未消费真实诊断聚合数据。以下能力均未实现，按可独立交付和验证的功能拆分；每一期完成后都可以保留为后续阶段的输入，不要求同一版本交付全部闭环。

### 第一期：竞品可见性

**目标：** 回答“同一批 AI 回答中，哪些已配置竞品被提及，而品牌是否缺席”。

- 在诊断配置中增加品牌级“竞品名称”逗号分隔输入；一个名称对应一个竞品记录，去重并限制最大数量。首期不提供竞品别名配置，与 GeoLook 的人工配置保持相同复杂度。
- 在每条已完成的 AI 样本中，以确定性、大小写不敏感的名称匹配记录品牌和竞品提及；保存命中的竞品、命中位置、解析器版本和无法判断状态。
- 增加竞品配置、样本提及和问题/引擎聚合的 Brand 范围 API；同一问题、同一市场、同一引擎只在相同有效样本集合中比较品牌与竞品。
- 在“诊断”下提供竞品对比视图，展示竞品出现率、品牌出现率、共同问题与品牌缺席问题；样本不足时显示“未测”，不显示 0%。

**验收边界：** 不执行竞品官网抓取、不生成竞品内容建议、不推断未配置竞争者；人工可在样本详情中标记误判，但自动纠正和别名管理留到后续阶段。

### 第二期：站点与页面体检

**目标：** 将当前基础抓取升级为可解释的“访问 → 定向 → 理解 → 可引用”诊断。

- 持久化页面级检查结果和站点发现项，记录规则版本、证据、严重度、受影响页面和上游阻塞关系。
- 增加 robots 规则与 AI UA 探测、X-Robots-Tag、sitemap/llms.txt、canonical、hreflang、JSON-LD、标题/正文重复和页面可引用段落检查。
- 提供资产审计视图与筛选 API，可按层、严重度和页面查看问题及证据。

**验收边界：** 只对已授权的公开 URL 抓取；不尝试登录、绕过访问控制或自动修改网站。

### 第三期：问题诊断与行动差距

**目标：** 将样本和站点证据转换为“为何不可见、优先做什么”的问题级结论。

- 为品牌问题增加意图/市场等元数据，并将探测题与指标题区分，防止探测题污染可见性统计。
- 按固定优先级输出“疑似负面、竞品主导、完全缺席、排名靠后、正常”五类结论；其中“竞品主导”依赖第一期的同口径竞品样本。
- 增加样本库和人工复核：查看原始回答、名称命中、引用链接/域名解析结果与人工判定；人工结论优先于规则结论，并保留审计记录。
- 聚合内容缺口、阵地缺口和事实偏差，产出可排序建议；渠道地图展示引用域名覆盖、关联问题和建设理由。

**验收边界：** 不以 LLM 黑盒直接给出结论；没有足够有效样本时只返回“未测/待人工”。

### 第四期：快照、报告与验证闭环

**目标：** 让诊断结果可回溯、可比较，并替换当前示例报告。

- 为完成的运行创建不可变快照，包含输入范围、覆盖率、规则版本、聚合指标、发现项和基线引用。
- 提供按问题、竞品、引擎、市场和周期的趋势/前后对比 API；只在两端均已测量时计算变化。
- 将诊断报告接入真实快照，展示竞品对比、引用表现、站点健康、渠道覆盖、未测状态和下一步建议；移除固定演示指标。
- 增加验证结果，关联诊断发现或后续工单，明确通过、失败、未测和需人工结论及其证据。

**验收边界：** 不在此阶段自动发布内容或自动修复网站；报告和验证只依据已保存的证据与规则结果。

## 分期依赖

第一期和第二期可并行；第三期依赖第一期的竞品/样本结果，并可逐步接入第二期的站点发现；第四期依赖至少一类稳定聚合结果，但可以先针对第一期的竞品可见性落地快照和趋势，再逐步纳入其他诊断维度。

- 各行业是否需要不同的严重度阈值、抽取块评分规则和阵地优先级？
- 首期“创建工单”应直接创建本项目的实体，还是先只导出关联建议？
