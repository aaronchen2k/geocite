## Context

GeoCite 现有变更 `geo-mvp-monitoring-attribution-dashboard` 定义了 AI 可见性监测、归因和报告的业务闭环，但尚未定义支撑其持续迭代的工程工作台：项目如何隔离、工作流如何执行、模型/沙箱如何管理、运行如何观测，以及失败后如何安全恢复。

本设计参考 `../xiao2` 已投入使用的方案，但不复制其“毕业设计助手”的业务语义。保留其中可迁移的通用模式：项目与迭代目录、NestJS 模块边界、SQLite/TypeORM 元数据、Speckit 命令编排、结构化状态文件、SSE/WebSocket 可观测性及项目级交付收尾。GEO 监测适配器、外部平台访问、归因评分和报告模板仍属于现有 GEO 业务变更。

关键约束如下：

- 运行结果必须可追溯到项目、迭代、命令、输入、产物与日志，不能只依赖浏览器内存状态。
- 不得通过绕过登录、验证码、反爬或平台条款来获得外部 AI 平台数据；执行运行时只负责合法调用已配置的适配器。
- 任意文件访问和命令工作目录必须限制在选定项目根目录；密钥不得写入状态快照、产物或日志。
- 项目工作台作为平台层，为现有和后续 GEO 能力提供运行基础，不改变 `geo-mvp-monitoring-attribution-dashboard` 的领域指标定义。

## Goals / Non-Goals

**Goals:**

- 建立清晰的 `Project → Iteration → Workflow Run → Stage Artifact` 层级，作为 GeoCite 研发和运营任务的统一边界。
- 以六阶段 Speckit 流程管理需求、设计、任务与实现，确保阶段产物和状态可恢复、可审核。
- 用运行时提供者抽象本地、Docker、OpenSandbox 和模型配置，以便业务模块不依赖某一种执行环境。
- 用 WebSocket 推送状态、SSE 推送日志，并提供回退、重做和检查问题恢复能力。
- 在项目收尾阶段从迭代声明与真实代码/配置证据生成可验证交付文档。

**Non-Goals:**

- 不迁移 `xiao2` 的学生、导师、待办、文档生成等业务模型或 UI。
- 不在本变更实现 GEO 监测任务队列、AI 平台爬取/调用、归因模型或报告模板。
- 不承诺所有执行提供者在首期同时上线；接口与状态模型先统一，提供者按可用性逐步启用。
- 不把单次模型响应或浏览器实时事件当作唯一事实源。

## Decisions

### 1. 采用“数据库元数据 + 项目目录产物”的双层事实源

SQLite/TypeORM 保存可查询的项目、模型配置、执行提供者和项目状态等平台元数据；项目根目录保存迭代规格、阶段产物、状态文件与日志。每个项目拥有 `rootPath`，每个迭代严格位于 `<projectRoot>/specs/<iterationDir>/`。阶段日志位于 `specs/<iterationDir>/logs/<stage>.log`，项目级状态和技术栈快照位于 `.specify/`。

这沿用 `xiao2` 的可携带产物模式：数据库不成为 Markdown/JSON 工作流工件的唯一持有者，因此项目可被审查、备份或在受控环境间迁移；数据库仍负责高效查询和管理。只用数据库会弱化工件可读性，只用文件会使项目管理、筛选和执行配置难以维护，因此不采用。

### 2. 以显式状态机编排六阶段 Speckit 流程

工作流顺序固定为 `kickoff → constitution → specify → plan → tasks → implement`。每次运行生成 `runId`，写入 `running/success/failed/cancelled` 等状态、当前阶段、命令、时间戳、错误及回退次数。阶段仅在前置产物和状态通过验证后启动；返回内容必须经结构化协议校验后才能推进状态。

状态同时保存在内存事件总线和项目目录的持久化快照中：内存用于实时广播，持久化用于刷新、重启和审计恢复。相较于纯前端状态或仅靠“文件是否存在”推断进度，这能区分成功、失败、过期和回滚后的产物。

### 3. 用执行提供者和命令协议隔离运行环境

定义 `ExecutionProvider` 接口，统一输入为项目根目录、迭代、Speckit 命令、模型解析结果、取消信号和受控环境变量；统一输出为结构化状态、stdout/stderr 摘要、退出码、产物路径和协议结果。首期兼容 `local`，预留 `docker`、`opensandbox`。模型配置以启用/默认状态管理，运行时只读取引用标识和必要连接参数，敏感凭据通过受保护配置注入。

该接口承接 `xiao2` 的 local/docker/opensandbox 选择能力，但使 GeoCite 的监测适配器能独立运行，避免将平台采集逻辑耦合进 Speckit 执行器。直接在工作流服务里分支启动不同进程会让日志、取消和错误处理不断重复，因此不采用。

### 4. 用“状态通道 + 日志通道”提供实时可观测性

WebSocket 负责运行状态、阶段切换、检查问题和完成/失败事件；SSE 负责可追加的日志，连接时先发送完整 snapshot，之后发送增量 `line` 事件与 keep-alive。日志按项目、迭代、阶段三级写入，HTTP/模型调用日志必须脱敏 authorization、cookie、token 等字段。

状态与日志分离能让页面在高频日志下仍保持稳定的工作流状态渲染，也便于日志页面断线后重新加载。只用 WebSocket 会提高日志回放和代理兼容复杂度，只做轮询会降低长任务可见性，因此不采用。

### 5. 回退和重做以依赖边界清理为准

回退仅允许指定到 `specify` 或 `plan`，重做允许从合法工作流阶段重新开始。系统在重置阶段时清理其后所有依赖状态、检查答案和过期产物引用，但保留历史日志、运行记录和可审计失败输出。对检查类阶段，用户答案绑定到原检查运行，再重跑对应阶段；禁止把恢复操作伪装成独立、无上下文的新步骤。

相比删除整个迭代目录，此方案保留问题复盘证据；相比无限制指定任意目标文件，显式状态机更容易验证不会造成半完成链路。

### 6. 项目收尾使用证据化技术栈与两阶段发布

项目收尾只纳入实现完成且未回退的迭代。它合并迭代技术声明，并扫描真实依赖清单、锁文件、容器/部署配置、ORM/schema/migration 与数据库配置，生成 `.specify/project-tech-stack.json`，包括声明、代码观测、最终能力、来源与冲突。技术栈一致时，在临时位置生成并校验 `quickstart.md` 与环境安装文档，全部通过后原子替换项目根交付物。

该选择遵循 `xiao2` 的收尾方式，避免让模型文本或 README 成为技术栈真源。简单合并声明会漏掉实现漂移，完全从代码推断会遗漏部署声明，故均不采用。

### 7. GEO 领域能力以模块契约接入平台层

`ai-visibility-monitoring`、`attribution-analysis`、`geo-reporting-dashboard` 作为项目作用域的领域模块。它们复用项目 ID、项目根、执行提供者、任务/日志通道和产物访问接口，但自行维护监测证据、归因规则、指标快照和报告业务表。平台层不解释品牌提及、信源权重或数字资产指数。

这样既能用同一工作台追踪 GEO 任务，也避免基础架构因行业指标变化频繁修改。把 GEO 表与工作流状态表混在一个模块会削弱边界，因此不采用。

## Risks / Trade-offs

- [外部执行器、模型服务或沙箱不可用] → 统一返回 `failed/unavailable` 状态、保留错误日志与退出信息；允许切换已配置提供者后从合法阶段重做。
- [状态文件与数据库元数据不一致] → 文件产物作为迭代工作流依据，数据库只存管理元数据；读写时做路径/状态校验并提供明确的修复建议。
- [并发运行覆盖同一迭代产物] → 以项目根、迭代和阶段组合键建立运行锁；启动、取消和完成时校验 `runId` 是否仍为当前。
- [日志或产物泄漏凭据] → 统一日志脱敏、最小化保存 stdout/stderr、将密钥放在受保护配置；下载/读取接口执行项目根边界校验。
- [生成的 quickstart 与实际代码漂移] → 用技术栈证据和关键内容校验阻断发布，失败时保留上一个可用版本。
- [将 xiao2 的业务复杂度不必要迁入] → 规格只吸收通用平台能力，领域模块以 GeoCite 的现有 OpenSpec 为准。

## Migration Plan

1. 建立项目、模型配置和执行提供者的元数据表，以及项目根目录初始化/路径校验服务。
2. 实现迭代目录、阶段状态、产物读写和基础工作流状态机；先以本地执行提供者验证单阶段闭环。
3. 接入 WebSocket 状态、SSE 日志、并发保护、回退/重做与检查问题恢复，并补充端到端测试。
4. 将 GEO 监测、归因和报告变更接入项目工作台的项目边界、任务/日志和产物接口，不改变其领域规格。
5. 实现项目级技术栈快照与交付文档原子发布；只有完成证据校验的迭代可纳入。
6. 按提供者逐步启用 Docker/OpenSandbox。回滚时关闭对应提供者或新入口，保留项目产物、日志和最近有效交付文档；不删除历史证据。

## Open Questions

- GeoCite 首期的默认执行提供者是本地受控进程还是 OpenSandbox；这将决定部署侧密钥与目录挂载的具体策略。
- 项目访问控制首期是否为单用户工作区，还是需要在项目元数据中立即增加 `ownerId/tenantId`。
- GEO 监测任务与 Speckit 开发迭代是否共用同一队列/运行面板，还是作为两个队列类型共享日志与审计基础设施。
