# 执行诊断后端设计

## 目标

一次执行诊断应保存可追溯的站点证据与 AI 问答样本，判断品牌官网是否能被 AI 访问、理解和引用。执行过程可实时推送给前端，单步失败不会阻断其余可独立执行的工作。

## 诊断范围与边界

- 站点范围：品牌配置的官网首页、robots.txt、sitemap 与 sitemap 可发现的站内页面。
- AI 范围：只运行品牌已选择、未禁用且已配置 API Key 的目标引擎。
- 第一批自动连接器：千问兼容模式 API；豆包方舟已开通内容插件时使用联网采样，未开通则标记为非联网样本。
- 没有官方 API 的网页端或 App 不能自动模拟登录采集，保留人工采样导入入口，并与 API 样本分开统计。
- 不依赖 Ahrefs、Semrush 等付费第三方 SEO 数据；搜索排名也不作为本期诊断的必需输入。

## 配置模型

`engines` 保存一个可采样的目标平台配置：名称、代码、厂商、模型名、兼容 API 地址、API Key 与启用状态。API Key 只保存在服务端数据库，任何 API 响应仅返回 `apiKeyConfigured` 与掩码。

`brand_engines` 是品牌和目标引擎的多对多关系。品牌管理的“诊断引擎”字段可多选；执行时只从该关联中筛选未禁用且已配置 Key 的引擎。未配置 Key 或已禁用的关联会记为跳过原因，不会悄悄忽略。

## 七步实际工作

1. 读取上一期快照和规则版本，作为本期对比基线。
2. 抓取首页、robots.txt、sitemap 和限定数量的站内页面，记录 HTTP 状态、规范链接、正文和元数据。
3. 使用浏览器 UA 与 AI 爬虫 UA（如 GPTBot、ClaudeBot）做差异探测，识别 robots、CDN/WAF、X-Robots-Tag 等阻断。
4. 从已抓取页面提取结构化数据、标题层级、可独立引用段落、重复内容与关键品牌事实。
5. 对每个可自动采样引擎，以固定问题库调用 API，保存原始回答、模型信息、请求时间、联网状态、引用链接及采样环境。千问必须使用其原生/兼容端点的联网能力；API、网页和 App 样本不可混算。
6. 将本期站点规则、问答提及、引用域名与上一期快照比较，输出可复核的变化与待处理项。
7. 汇总步骤结果、样本摘要和原始证据，生成不可变的运行快照与报告索引。

## 执行器设计

执行器以运行记录为中心。每一步在开始、关键事件、成功或失败时写入 `execution_diagnosis_events`，并通过 SSE 推送。运行日志额外落在 `logs/<brand-code>/execution-diagnosis-<本地时间>-run-<id>.log`，便于排查与归档。

站点抓取、引擎采样和报告生成应拆成可重试任务。每项任务带超时、有限重试和取消检查；单个引擎失败只会使该引擎样本失败，本次运行仍能以 `partial` 状态完成。原始回答和抓取证据应增量写库，避免进程中断丢失已完成样本。

## 后续需要新增的数据

- `execution_diagnosis_engine_runs`：一次运行内每个引擎的调度状态、模型版本、联网状态、耗时和错误。
- `execution_diagnosis_samples`：问题、回答原文、命中品牌、竞品、引用链接、采样环境和人工复核结果。
- `execution_diagnosis_pages`：抓取页面与访问/结构/可引用性证据。
- `execution_diagnosis_findings`：可分配的诊断发现、严重度、证据和建议。

上述表与现有运行、步骤、事件表关联；运行完成后不覆盖历史记录，后续周期通过运行 ID 做前后对比。

## 千问接入约定

千问使用 OpenAI 兼容模式端点。诊断调用时从 `engines` 读取 `modelName`、`baseUrl` 和 API Key；密钥不进入 SSE 事件、Pino 日志、步骤结果或前端。请求和响应应记录脱敏后的模型、状态码、耗时、联网能力和引用数量。正式启用联网采样前，需要在千问平台确认该模型与账号已获得相应搜索能力。

## 验收标准

- 品牌可多选目标引擎，关联可在品牌详情和保存后读回。
- 新运行仅调度已关联、已启用且已配置 API Key 的引擎，并记录未调度原因。
- API 响应、SSE、运行结果及日志中不出现 API Key。
- 运行过程可取消、可恢复读取历史，某个引擎或页面失败不会丢失其他证据。
- 同一问题库和模型版本跨周期复用；报告清楚标注 API、网页、App、联网与非联网样本的差异。
