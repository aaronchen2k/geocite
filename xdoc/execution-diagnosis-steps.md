# 执行诊断的八个步骤

执行诊断的目的，是确认已经做过的 GEO 优化是否真的产生了效果。它只收集证据、执行检查和给出结论，不会修改网站内容或外部平台配置。

| 步骤            | 做什么 | 通俗理解 | 主要产出 |
|---------------| --- | --- | --- |
| 1. 读取上次基线     | 读取上一次成功检测的快照、规则和工单目标。 | 先拿出“上次体检报告”，确定这次该和什么比较。第一次检测没有历史记录时，会标记为首测。 | 可比较的指标清单和基线版本。 |
| 2. 抓取网站内容     | 重新访问首页、robots.txt、站点地图、llms.txt 和关联页面，记录响应与页面内容。 | 像重新走访一遍网站，确认现在能访问哪些页面、页面实际返回了什么。 | 本次抓取到的页面、成功与失败数量、HTTP 响应证据。 |
| 3. 站点AI可触达性检测 | 分别用普通浏览器和 AI 爬虫的身份访问网站，并检查 robots、CDN/WAF、禁止抓取标记等。 | 确认人能打开的网站，AI 是否也能正常进入和读取；避免只对 AI 爬虫返回 403 或被拦截。 | AI 爬虫可访问性结论、被拦截的原因和对应证据。 |
| 4. 页面与内容体检    | 检查页面结构、规范链接、结构化数据、正文质量和可引用段落。 | 查看网站内容是否清楚、规范，AI 是否容易理解并摘取其中的信息。 | 页面问题清单、受影响页面和内容覆盖情况。 |
| 5. AI 回答采样    | 在已配置且允许使用的 AI 引擎中，按问题和市场获取回答并保存引用信息。 | 直接问 AI 一组真实问题，看看它会不会提到品牌、引用哪些内容、答案是否正确。 | 问题级回答、引用证据、有效样本和排除原因。 |
| 6. Playwright 网页复核 | 对第 5 步已冻结的“引擎 × 问题”样本，在本机专属 Chrome Profile 中复核。所有核心业务能力问题、API 已提及当前品牌的问题都会入选；其余未命中非核心样本随机抽取 25%，不足 API 总样本 30% 时再补齐。 | 用真实登录后的网页环境核对关键回答；随机种子、入选原因和结果会随运行快照保存，之后不会变化。 | 独立网页回答、截图路径、提及判断、排除原因和完成时间。 |
| 7. 规则验收与前后对比  | 使用成功的网页复核结果作为优先校正来源，并和上次基线比较。没有成功复核时保留 API 参考，但不把它伪装为网页结论。 | 像验收工单：哪些目标达成了、哪些仍未达标、哪些证据不足需要人工确认。 | 通过、未达标、待人工和未测的结论，以及变化值。 |
| 8. 生成检测结果     | 汇总运行过程、步骤事件、发现项和结果摘要，并保存为可追溯快照。 | 把这次体检整理成一份可以回看、分享和再次比较的报告。 | 检测运行记录、结果摘要和可复用的历史快照。 |

## 如何理解结果状态

- **通过**：该项检查已完成，且结果符合目标或规则。
- **未达标**：检查完成，但发现明确问题，例如 AI 爬虫被 CDN 拦截。
- **待人工**：系统已发现线索，但需要人工结合业务背景确认。
- **未测**：缺少授权、配置、页面证据或必要输入，不能把它当作失败或通过。
- **部分完成**：至少有一部分网页复核成功，但另一些引擎因未就绪、登录失效、验证码、风控或网页异常被排除；这不会把 API 样本或品牌结论记为失败。

关闭“使用 Playwright 网页复核”后，第 6 步会显示为已跳过，原因固定为 `playwright-web-review-disabled`；第 5 步 API 采样仍照常执行。

步骤执行完成只说明该步骤已经跑完；具体的检查是否通过，要看该步骤内的检查结论。
